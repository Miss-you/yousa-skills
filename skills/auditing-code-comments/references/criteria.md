## 删除标准

### D1 复述代码在做什么

代码已经说了的，注释再说一遍就是两份待维护的真相。

```go
// ❌ 把 taskId 作为 field 写入 hash，然后设置过期时间
rdb.HSet(ctx, k, taskID, raw)
rdb.Expire(ctx, k, ttl)
```

### D2 设计论证：为什么选 A 不选 B

搬进设计文档，代码里最多留一行指路。

```go
// ❌ 12 行论证「为什么用 Hash 不用 String、为什么不需要 Lua、
//    最初设计是全量覆盖所以需要 CAS，改成单条写入后那个问题就不存在了……」

// ✅ 用 Hash 让「登记一条」「删除一条」各自是单条命令，并发按 field 天然隔离，
//    因而不需要 Lua 或版本比对。取舍见 design.md 的 D1。
```

判据：这段话是在回答**「当初为什么这么定」**还是**「现在改它要小心什么」**。前者搬走。

### D3 复述评审过程

`// 有意见认为 X，但漏了 Y`、`// 上一轮 review 指出……`——这是决策记录，属于 change / PR 描述，不属于代码。

### D4 已被测试名钉住的行为

测试函数名就是那句说明，而且它会随代码一起跑、不会烂。

```go
// ❌ // 幂等路径也必须回带投影，否则写失败永远修不好
//    （已有 TestIdempotentRetryReturnsProjection）
```

### D5 引用了已不存在的东西

脚本第三块的输出。删掉代码没删注释是最常见的腐烂来源，也是「注释多」真正的代价。

跨仓 / 跨服务的符号引用会被误报，人工确认后保留，但**必须写清它在哪个仓**，否则下一个人无从验证。

### D6 每个字段都配一句「这是什么」

字段名已经说了的不要重复。只给**看不出来**的字段写。

```go
// ❌
type Task struct {
    UserID   int64  // 用户 ID
    TaskID   string // 任务 ID
    ExpireAt int64  // 过期时间
}

// ✅ 只标注反直觉的那处
type Task struct {
    UserID   int64
    TaskID   string
    ExpireAt int64
    // ⚠️ 对端启用了 int64→string，报文里这几个是字符串，tag 不是笔误
}
```

### D7 给「正常预期分支」写的解释

正常流程不需要解释。只有**反直觉**的分支才需要。

## 保留标准

### K1 违反直觉的决策（照直觉改会出事）

这是唯一值得多行的一类。必须能一句话说出「改了会发生什么」。

```go
// ✅ 刻意不删这条解析失败的记录：解析失败最现实的成因是我们自己的解析器与报文漂移了，
//    那种情况下所有记录都解不开，自动删除会在高频入口上把所有待处理任务一次性销毁。
```

### K2 外部契约的坑

跨仓字段形态、框架陷阱、协议约定——这些在代码里看不出来，且改错了是静默失败。

```go
// ✅ Body 必须是 string 且 base64 由本包自己做：框架换掉的序列化器会把 []byte
//    编成 \xNN 而不是 base64，对端解不开。
```

### K3 破坏性操作的护栏

删除、覆盖、状态迁移处的「为什么不能这么改」。

### K4 运维怎么用

告警怎么配、指标触发后该查什么方向。这类信息不在代码里，也不在设计文档里（那是给开发看的）。

### K5 导出符号的契约

调用方必须知道、但从签名看不出来的：返回空和返回 error 语义有何不同、失败了调用方必须做什么。

## 压缩手法

**多段论证 → 一句结论 + 指路。**

```go
// 改前（8 行）：完整论述为什么两条失败路径要用不同错误码……
// 改后（2 行）：
// 两类失败返回不同的码：报文问题重建无用，Redis 问题重建即可。
// 对端只展示这句文案，下游人工据此处理。
```

**并列展开 → 收成一句共性。**

```go
// 改前：分别列出 taskId / userId / expireAt 三个字段缺失各自的后果，每条 2-3 行
// 改后：
// 三个零值不可能来自合法报文，一定是契约漂移；不拦的话全链路零 ERROR、
// 零计数器，对端还以为调用成功了。各字段的具体后果见 design.md。
```

**⚠️ 标记留给真正会出事的地方。** 满屏都是 ⚠️ 等于没有 ⚠️。一个文件里超过 2-3 处就该重新掂量。

## 出处

这套标准调和了两派常被对立引用的意见：

- **Ousterhout,《A Philosophy of Software Design》**：注释应当记录设计者知道、但代码表达不出来的信息；**接口注释是最有价值的**。
- **Martin,《Clean Code》**：注释是「未能用代码表达清楚」的补偿；且注释会随代码演进而说谎。
- **Kernighan & Pike,《The Practice of Programming》**：不要给烂代码写注释——重写它。

调和方式就是 SKILL.md 里那条**按位置分**的规则：接口/契约边界上 Ousterhout 对（注释是资产），实现内部 Martin 对（注释是负债）。争论其实源于两派谈的不是同一个位置。
