# 注释减法审查

## 为什么需要这个 skill

常规 review 全是**加法**：`code-review` 让你补错误处理，`3am-debuggable` 让你补留痕，指标类 review 让你补指标说明，每条发现修完你都会顺手写一段「为什么这么改」。

**没有任何一个岗位负责删注释。** 连 `overengineering-audit` 都不行——它的反模式表里明确写着「解释**为什么**的注释：不要砍」。

于是注释单调增长，而且增长最快的恰恰是刚被反复 review 过的代码。这个 skill 是唯一的减法通道，**必须放在所有其它 review 之后**。

## 硬约束

**只看注释，不改代码逻辑。** 发现代码本身的问题就记下来告诉用户，不要顺手改——那会让这次 diff 变得无法审阅。

**只审本次改动**：`git diff`（含 staged）+ 未跟踪文件。未变更文件的注释一律不动，看到了单独说。

## 核心判据

> **代码注释回答「改这里要小心什么」；设计文档回答「为什么这么设计」。**

把后者写进代码，等于同一份推理维护两遍，而代码那份必然先烂——因为改代码的人不会想起来去改注释。

位置决定价值：

| 位置 | 注释的性质 | 尺度 |
| --- | --- | --- |
| 包 / 导出符号 / 接口方法 | **契约**，是资产 | 2-4 行，说清调用方必须知道什么 |
| 函数体内部 | **实现论证**，是负债 | 0-2 行，说不出「照直觉改会出什么事」就删 |

## 工作流

### 1. 跑脚本拿线索

在被审仓库的根目录下运行，脚本路径指向本 skill 的安装位置（下面以 `~/.claude/skills/` 为例）：

```bash
python3 ~/.claude/skills/auditing-code-comments/scripts/comment_audit.py          # 自动取 git diff + 未跟踪文件
python3 ~/.claude/skills/auditing-code-comments/scripts/comment_audit.py FILE...  # 或指定文件
```

输出三块，都是**线索不是判决**：

- **密度对照**：本次文件 vs 仓内同类文件基线（测试与非测试分开比）。看的是**偏斜**不是总量——总量达标但某个文件 3 倍于基线，问题在那个文件。
- **函数体内的长注释块**：最可能是该搬进设计文档的论证。
- **注释提到但代码里已不存在的标识符**：注释烂在原地的直接证据。跨仓引用会误报，人工确认。

### 2. 逐条过三个问题

对每一段注释按顺序问，任何一个命中就删或压缩：

1. **删掉它，下一个人会不会改错？** 不会 → 删。
2. **它说的事，代码本身 / 测试名 / 设计文档里是不是已经有了？** 有 → 删，重复的那份必然先烂。
3. **它引用的东西还在吗？** 不在 → 修或删。

活下来的再问一句：**能不能压到 1-2 行？** 判据是「照直觉改会出什么事」这一句必须留住，其余的推理搬进设计文档。

### 3. 分类处置

删除标准与保留标准见 [references/criteria.md](references/criteria.md)，含每类的正反例。审查时读它。

### 4. 报告

先给密度前后对比，再按文件列出**删了什么、为什么**。把「搬进设计文档」的内容明确写出来放到了哪个文件的哪一节——搬走不等于丢掉，读者要能追过去。

发现的注释腐烂（引用已删除的符号）单独列一节，那是最有价值的产出：它证明了「注释多」不是风格问题而是维护问题。

## 收敛条件

改完后注释行数必须下降。若某文件反而变多，说明在给注释写注释，回退。

不要为了压比例而删掉「照直觉改会出事」的那几处——这个 skill 的目的是让剩下的注释**被人读**，不是把数字做低。一个文件只剩 3 行注释但每行都拦住一次事故，好过 30 行没人看。
