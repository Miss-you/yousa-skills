## F1 正交能力被焊成互斥状态

**配置形态**：`pushV2GraySub` / `pushV2GrayExt` / `pushV2GrayChat`（三档场景开关，即 F4 收敛后的结果）+ `pushV2Cutover`（出口切换）。

**代码原本的模型**：一个三态枚举。

```
outletLegacy → 走旧出口，不对账
outletShadow → 走旧出口 + 请求体对账     ← 对账焊在这里
outletNew    → 走新出口，不对账
```

**运维怎么配**：dev 环境自测，四个 key 全部 `{"mode":"on"}`。理由不需要解释——**全打开就是全打开**。

**实际发生了什么**：场景 key 命中 + cutover 命中 → 所有用户被划进 `outletNew` → shadow 组为空 → **对账一次都不跑**，日志里一条 parity 记录都没有。开发者盯着日志以为链路没通，实际上是配置「太开」了。

**为什么设计时看着没问题**：三态枚举在流程图上完全自洽，每个状态都有明确语义，状态转移也画得出来。问题不在状态机，在于「对账」和「走哪条出口」根本是两件正交的事，被压进了同一个维度。压扁之后，**四种现实需求里只能表达三种**，而丢掉的那一种（切过去了还继续对账）恰好是放量期最需要的。

**修法**：出口降回两态，对账提成独立开关。

```
出口 = 场景key命中 && cutover命中 ? new : legacy
对账 = pushV2Reconcile 命中              ← 与出口无关
```

三态降两态，概念更少，可表达的组合从 3 种变成 4 种。

**推广**：任何 `enum { A, A+B, C }` 形状的状态机都要警惕——`A+B` 里的 `B` 是不是一个独立能力被顺手挂上去了？判据是问「B 会不会有人想在 C 状态下也要？」

## F2 缺省方向沿用了既有开关

**配置形态**：迁移开关直接复用既有的 `flagOn`。

**既有语义**（不能改，多处存量调用依赖）：

| 情况 | flagOn |
|---|---|
| 配置不存在 / 空串 | **true（全开）** |
| mode=off | false |
| JSON 非法 | false |

「未配置 = 全开」对存量功能是对的：开关是给已上线功能做**急停**用的，方向天然向开。

**用作迁移开关时的后果**：三件事在日志和监控上长得一模一样——key 名打错一个字、新环境漏建、配置中心抖动返回空串——全都表现为「开关看起来没配」。而缺省向开意味着这三种情况都会把 **100% 流量一次性打进未经验证的新出口**，且没有任何告警。

**修法**：另起 `migrationFlagOn`，共用同一份配置结构（`mode`/`percent`/`allowList`）与同一段命中判定 `matchRollout`，**只反转缺省这一个语义**。差异全部收在「取配置 + 缺省怎么算」的前置逻辑里，命中判定不复制第二份——复制会让灰度分桶口径在两个开关之间悄悄漂移。

**推广**：新开关复用既有读取函数时，一定要跟进实现看缺省分支，不能看调用处的注释。存量开关的缺省方向是历史需求的产物，与新需求大概率相反。

## F3 采样单位与运维读到的不是一回事

**配置形态**：`{"mode":"gray", "percent":1}` —— 运维读到的是「1% 采样」。

**代码实际**：`percent` 按 userId 逐个判定，触发条件是「这批用户里**任一人**命中就触发」。

**用在群聊消息上**：一条 500 人的群聊，`P(至少一人命中) = 1 - 0.99^500 ≈ 99.3%`。运维配了 1%，实际近似全量。

**为什么难发现**：分桶逻辑 `userID % 100 < percent` 本身完全正确，单元测试也过。错的是**它被用在了批量场景**，而「采样单位」这个概念在代码里根本没有名字，没人会去 review 一个不存在的东西。

**修法**：对账比的是请求体，与用户数无关，采样单位应该是「一次下发」而不是「一个用户」。改成按这批接收者里的第一个人判定。

**推广**：任何 ratio / 百分比配置都要显式回答「采样单位是什么」，并写进给运维的说明。批量接口上尤其要问：单位是一个元素还是一个批次？

## F4 粒度切得比运维会用的更细

**原方案**：每个通知场景各一个 key——低频通知 A / B / C、跨服务发起的通知、高频即时消息，共五个。

**用户的反馈**：key 太多了，放量排期里也没有时间逐个去开。

**判据不是数量，是放量步骤**。把真实节奏写出来：

| 第几步 | 开什么 | 风险 |
|---|---|---|
| 1 | 低频通知 A / B / C | 低，量小，出问题影响面窄 |
| 2 | 跨服务发起的通知 | 中，跨服务链路 |
| 3 | 高频即时消息（单聊 / 群聊） | 高，量最大，最后放 |

低频通知 A / B / C 在任何一步里都是**同开同关**的——没有哪个现实节奏会只开 A 不开 B。合并成一个 key。而高频即时消息必须单独一个，它的风险等级和前面差一个数量级。

五个场景 key 收敛成三个（即 F1 里的 `Sub` / `Ext` / `Chat`）。

**推广**：先写放量步骤表，再定 key 数量。步骤里总是一起动的合并；一个 key 同时控着风险差一个数量级的两件事就拆开。

## F5 隐藏档位与生效时延没写进说明

两个小问题，一起说：

**隐藏档位**：`mode` 的取值是 `off`=关 / `on`=全开 / `gray`=按灰度（`percent` 命中或在 `allowList` 里）。`gray` 完全猜不到——运维只会试 off 和 on，永远发现不了白名单能力的存在。给运维的说明必须列全枚举。

**生效时延**：新旧两侧服务读配置时都有分钟级本地缓存。没写进说明时，运维配完立刻验证、没反应、以为配错了，会反复改——最坏的情况是把已经配对的值改坏。说明里写一句最长多久生效，就能省掉这一整轮。

**推广**：给运维的说明至少要有五项——取值枚举、配置顺序、生效时延、怎么确认生效、怎么回滚。

## 为什么 code review 抓不到这类问题

F1、F3、F4 都通过了设计评审和多轮 code review。原因是同一个：

**review 的人和写的人共享同一个心智模型。** 打开代码，`outletShadow` 这个名字连同它的注释一起告诉你「这是旧出口发送 + 对账」，你会点头，因为你读的就是作者的意图。三态枚举自洽、状态转移完整、单测全绿。

运维没有这个模型。他手上只有 key 名和一句说明，于是他做了唯一合理的事——**全打开**。这个动作在代码模型里根本不是一个被考虑过的输入。

所以本 skill 的核心动作是**强制换一次视角**，而且规定了顺序：先只看 key 名把「预期」列写完，写完才准读代码。顺序反了，你写出来的「预期」就是代码逻辑的复述，这一步就白做了。

这和先写测试再写实现是同一个技巧——先固定住一个独立于实现的判据。
