# 技术方案验证文档：格式参考

## 文档元信息

文件名建议：`{需求简称}-技术验证.md`，放在项目约定的文档目录（如 `docs/`）；项目按版本组织文档时可加 `v{version}-` 前缀。

```markdown
# {需求名称}技术方案验证文档

**需求链接**：[Jira/Issue #{issue_id}]({url})
**文档状态**：验证中
**最后更新**：{YYYY-MM-DD}
```

文档状态流转：`验证中` → `验证完成` → `决策中` → `已归档`

---

## 标准章节结构

### 1. 需求背景（必填）

一段话说清楚：要做什么、为什么做。聚焦问题，不要展开方案。

### 2. 能力/技术验证（按调研阶段分节）

每个被验证的能力/组件/接口单独一节，例如：

```markdown
## 2. {外部能力}验证

### 2.1 接口/能力描述

说明能力的来源（第三方 SDK / 内部服务 / 配置项），提供文档链接。

### 2.2 关键决策：{决策点}

**结论**：XXX

| 问题 | 结论 |
|------|------|
| 是否需要升级/迁移？ | 不需要 / 需要，原因：XXX |
| 是否有服务损耗？ | 无 / 有，影响范围：XXX |
| 能否直接使用？ | 是 / 否，前置条件：XXX |

> ⚠️ **待验证** / ✅ **已验证**：描述还需要做什么，或验证结果。
```

### 3. 现状分析与问题（存量的坑）

逐条描述现状中的限制、不一致、潜在风险：

```markdown
## 3. {模块名}现状与问题

### 3.1 {子问题}

描述当前状态，用表格对比不同情况：

| 维度 | 现状 | 影响 |
|------|------|------|
| ... | ... | ... |

### 3.2 {子问题}

- 说清楚"是什么"，以及"为什么是问题"
- 标注信息来源（文档链接、代码路径、与谁核实）
```

### 4. 长期目标方向（可选）

描述理想状态，以及达到理想状态的关键路径或依赖。

```markdown
## 4. 长期方案目标

**目标**：XXX

**关键路径**：
1. 推动 {外部依赖} 做 XXX
2. 客户端修改 XXX
3. 后端实现 XXX
```

### 5. 待办事项（按阶段）

```markdown
## 5. 待办事项

### 阶段一：{目标}（状态：进行中 / 已完成 / 待启动）

- [ ] 具体行动项，说明验证方法或交付物
- [ ] 具体行动项

### 阶段二：{目标}

- [ ] 具体行动项
```

阶段划分原则：
- **阶段一**：后台自己能做的技术调研/验证
- **阶段二**：需要跨团队配合的确认（客户端、第三方、DBA 等）
- **阶段三**：基于前两阶段结果的决策/排期

### 6. 限制与约束汇总（必填）

把所有"坑"集中到一张表，便于快速查阅：

```markdown
## 6. 限制与约束

| # | 约束描述 | 影响 | 应对方式/备注 |
|---|----------|------|--------------|
| 1 | 具体约束 | 具体影响 | 已有方案 or 待解决 |
| 2 | ... | ... | ... |
```

---

## 写作原则

1. **决策要有结论**：每个调研点必须给出明确结论，不要只描述现象
2. **坑要标注来源**：是文档中发现的、代码中发现的、还是与谁确认的
3. **待验证要显眼**：用 `⚠️ **待验证**` 标注，便于后续 grep 查找未闭合项
4. **避免写"计划"**：文档记录已发现的事实和决策，不要写未来可能的方案
5. **不写时间线**：不写"下周做什么"，只写"需要做什么"和"当前状态"

## 案例参考（虚构）

示例：`large-file-multipart-upload-技术验证.md`

该文档覆盖了：
- 云存储 SDK 分片上传并发参数的验证结论（是否需要升级、参数是否有文档保障）
- 跨端不一致问题（Web 与桌面端判定文件类型的方式不同，校验规则无法共用）
- 按阶段拆分的待办（后台自查 → 前端核实 → 决策排期）
- 约束汇总表（含依赖未文档化参数的风险、SDK 升级兼容性等）
