# 技术方案验证文档 SOP

## 概述

技术方案验证文档记录的是"调研/验证阶段"的事实与决策：某个外部能力能不能用、存量系统有哪些坑、接下来按什么顺序推进。它不是最终技术方案，也不是上线计划。目标是让后来的维护者不翻聊天记录，就能看清哪些结论已闭合、哪些还悬着。

文档格式和章节模板见 [references/template.md](references/template.md)。

## 何时使用

- 用户手里有零散的调研材料（聊天截图、会议笔记、口述、代码阅读笔记），想整理成一份文档
- 正在验证某个第三方 SDK / 外部接口 / 内部系统的能力，需要沉淀结论和限制
- 需求还在"能不能做、怎么做"阶段，还没进入排期和发布

不适用：已经确定方案、要写正式技术设计或接口文档时，改用对应的技术文档流程。

---

## 第一步：对原始材料做分类

拿到原始材料（聊天截图、会议笔记、口述）后，先做信息分类，不要急着写：

| 信息类型 | 识别特征 | 处理方式 |
|----------|----------|----------|
| **已确认结论** | 有来源（文档/代码/某人确认）、有明确是/否 | 直接写入，标注来源 |
| **待验证项** | "应该可以"、"理论上"、"需要测试" | 写入 ⚠️ **待验证**，列入待办 |
| **已知的坑** | 限制、不一致、外部依赖、非公开能力 | 正文描述 + 汇总到约束表 |
| **背景信息** | 为什么做、业务目标 | 压缩成一段话放需求背景节 |
| **行动项** | 需要做什么、找谁确认 | 按阶段归入待办节 |

---

## 第二步：定文档骨架

按"验证对象"组织章节，**不按时间线**：

- 每个被验证的外部能力/系统/接口 → 独立一节
- 跨平台/多端的现状对比 → 独立一节
- 长期目标（如有明确方向）→ 独立一节
- 待办事项 + 限制约束 → 固定放最后两节

材料少时合并章节，不要为格式凑内容。

---

## 第三步：三个关键写法

**① 结论前置**：每个调研点先给结论，再给支撑。读者不应翻到最后才知道答案。

**② 未闭合项用 ⚠️ 显式标注**：
```
> ⚠️ **待验证**：XXX 需要实测/跨团队确认。
> ✅ **已验证**：XXX，结论为 YYY（来源：ZZZ）。
```
这让文档可以 grep `⚠️` 找出所有未闭合项。

**③ 坑必须集中汇总**：正文里分散描述每个坑，但最后一节必须有一张汇总表。散落在各节的坑容易被忽略，汇总表才能让维护者快速评估风险全貌。

---

## 第四步：待办按阶段拆分

阶段边界的判断依据是**执行主体和前置依赖**，而非时间：

- **阶段一**：当前团队自己能做的（技术调研、代码验证、内部测试）
- **阶段二**：需要外部团队配合才能推进的（客户端确认、第三方接口验证、DBA 评估）
- **阶段三**：需要基于前两阶段结果才能做的决策（排期、方案选择、跨团队对齐）

---

## 不写什么

- ❌ 上线计划 / 灰度策略 / 发布时间表
- ❌ 详细测试用例
- ❌ 未来"可能"的方案（只写已确认的方向）
- ❌ 时间估算

---

## 示例

输入（口述 + 聊天记录摘要）：
> 想让大文件上传走对象存储的分片上传。某云存储 SDK 好像能调分片并发数，但文档里没写；另外 Web 端和桌面端判定文件类型的方式不一样，得找前端确认。

产出骨架：
1. 需求背景：一段话说明为什么需要分片上传
2. 云存储 SDK 分片并发参数验证：结论前置（可用 / 不可用 / ⚠️ 待验证），注明该参数文档未列出
3. 多端现状对比：表格列出 Web 与桌面端文件类型判定差异及影响
4. 待办：阶段一后台自查 → 阶段二前端确认判定逻辑 → 阶段三决策排期
5. 限制与约束汇总表：依赖未文档化参数的风险、SDK 升级兼容性等

---

## 常见错误

- **按时间线写**：照聊天顺序罗列"先问了 A，后来 B 说……"。应按验证对象组织章节。
- **结论藏在最后**：先铺垫大段现象再给答案。每个调研点应先给结论。
- **把猜测当结论**："应该可以""理论上支持"直接写成事实。没有来源的一律标 ⚠️ **待验证**。
- **坑只散落在正文**：没有最后的约束汇总表，维护者无法快速评估风险全貌。
- **待办按时间切分**：写成"本周/下周"。应按执行主体和前置依赖分阶段。
- **混入计划类内容**：上线计划、灰度策略、时间估算、未确认的"可能方案"都不属于这份文档。
- **为格式凑内容**：材料少时硬撑出六个章节。应合并章节，只保留有实际信息的部分。
- **结论不注来源**：读者无法判断可信度。标注是文档、代码还是哪方确认的（写角色，如"客户端负责人"，不写人名）。
