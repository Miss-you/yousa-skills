# 改动范围审计

## Overview

**发现 ≠ 决定。** 助手可以发现任何问题。一处改动能不能进这次提交，只看两件事：用户有没有明确要过它，被改的东西归不归用户管。

这是一道工序，不是一条戒律。基线测试里，没有任何指导的模型被明确问到「这些改动都该提交吗」时，9 次全部判对。出事的原因是没有人问这个问题，以及后面每一步检查对照的都是助手自己写的方案。所以本 skill 只规定三件事：什么时候问、拿什么来对照、输出什么。

原则与出处见 [references/principles.md](references/principles.md)。

## When to Use

两个检查点，都要做：

| 检查点 | 时机 | 审什么 |
|---|---|---|
| 方案检查 | 任务表写完、动手之前 | 每个任务 |
| 提交检查 | 所有 review 的修复做完、减法做完、提交之前 | 每个改动块 |

提交检查放在流水线最后一步。review 的修复本身就是越界改动的来源，放在 review 之前会漏掉它们。

不适用：用户明确说过「看到的问题顺手都改掉」。

## 输入契约

三样都齐了才开始，缺哪样先补哪样。

**1. 授权台账**

逐条引用用户的原话，每条写明它授权了什么。助手自己提出的建议单独列出，逐条标注：

| 用户之后的反应 | 状态 |
|---|---|
| 明确点名同意（「那个比较逻辑也改掉」） | 已授权 |
| 回了别的话题、没有回应、只说「继续」「开干」 | 未授权 |
| 批准的是整份方案，但没有逐项看过 | 未授权 |
| 事先给的概括性指令（「review 有问题就修」「你看着办」） | 只覆盖本次新写的代码，不覆盖既有代码 |

台账里不能出现助手的转述、助手写的方案、助手归纳的「目标」。

**2. 归属**

被改文件归谁：`OWNERS` / `CODEOWNERS`、用户在会话里说过的话（「这个模块不是我负责的」）、`git log` 的主要作者。

**3. 改动清单**

```bash
python3 <skill-dir>/scripts/scope_inventory.py            # git / svn 工作区
python3 <skill-dir>/scripts/scope_inventory.py --help     # 其他用法
```

`<skill-dir>` 是本 skill 所在目录，在被审计的仓库根目录下运行。

输出逐文件的「新增 / 纯追加 / 改了既有行 / 仅格式 / 无文本差异（二进制、权限、重命名）」、是否配置或依赖清单、OWNERS 是否包含当前用户（CODEOWNERS 按该路径最后一条匹配规则判断）（`--me` 填用户在 OWNERS 里的名字，默认取 git 用户名）。它只清点，不下结论。

## 逐块分类

每个改动块（方案检查时是每个任务）给一个结论，按顺序问三句：

1. 撤掉这一块，用户原话里的目标还能验收吗？
2. 这一块改变了谁的行为：只有新功能，还是已有的调用方、其他数据类型、其他接口？
3. 被改的文件归谁？

| 类 | 判据 | 处置 |
|---|---|---|
| A 目标内 | 能指到台账里某条用户原话；撤掉后目标达不成；不改变既有行为 | 提交 |
| B 目标必需，但动了既有行为或别人的模块 | 撤掉后目标达不成或有缺陷，同时第 2、3 问的答案超出了用户自己的新功能 | 停下来问用户，写清不改的后果；得到明确答复前不提交 |
| C 顺带 | 撤掉后目标照样达成：review 建议、顺手修的 bug、格式化、改名、日志、注释、配置默认值、多余的依赖升级 | 还原，记入移交清单 |
| D 来源不明 | 说不出它为什么在这里 | 还原 |

补充判定：

- **同一个改动块里混了不同类**（比如一处比较逻辑和一行日志在同一个 hunk）：拆到行，分别给结论。
- **用户明确要求在别人的模块里新增**：新增文件和纯追加仍是 A，同时在输出里提示这次提交需要 owner review。
- **B 和 C 的分界看后果落在谁身上**：不改会让用户自己的目标有缺陷的，一律 B，摆到用户面前。证据不足不改变归类，体现在输出里：列出哪些前提没有核实，默认处置写「不进」。后果落不到用户目标上的才是 C。
- **「必需」由提出者举证**：可复现的证据是失败的测试、报错、日志。理由只出现在助手自己的方案或分析里的，不算已证实。
- **新增文件按文件审**，不逐字段对回原话，除非它带来了用户没要过的对外行为。
- **依附的测试、注释**在表里写「B（跟随）」「C（跟随）」。

## 长会话用干净上下文复核

会话很长，或者自己就是这些改动的作者时，派一个 subagent 做分类，只给它三样输入：授权台账、归属、补丁。不给方案，不给每处改动的理由，不写「已定的设计决策不要重新讨论」。作者对照自己的方案自审，方案里已经越界的任务会原样通过。

不能派 subagent 时自己做：只对照台账里的用户原话，不打开自己的方案，并在输出里注明「未经独立复核」。

## 输出契约

```markdown
## 结论
现在可以提交：<文件列表>
需要还原：<文件或行>
等你决定：<B 类一句话>

## 授权台账
用户原话 → 授权了什么；助手提过的建议 → 用户的反应 → 状态。

## 逐块分类
| 文件 / 改动块 | 类 | 授权依据（用户原话）或缺失说明 | 处置 |
|---|---|---|---|

## 待用户决定（B 类）
问题、不改的后果、改的后果、当初哪些论断没有核实、可选做法、推荐哪个。

## 移交清单（C 类，不改代码）
问题、证据 file:line（用改动前的行号）、影响、建议改法、应交给谁。
```

- B 类没定之前，A 类可以先提交，B 类那几处不进。
- B 类可以给推荐做法，决定权留给用户。被改文件不归用户时，问用户的是「要不要去找 owner」，怎么改由 owner 定。
- C 类还原后会影响用户眼前的事（提测、联调）时，在结论里单独提醒一句。
- 移交清单写进方案文档或 issue，不写进代码；没有可写的地方时写在回复里。
- 被改文件不归用户时，C 类只移交，不提议「单独再提一个 commit」，除非用户要求。
- C、D 类由助手还原自己加进去的改动，还原后重跑构建和测试，确认剩下的改动能独立通过。还原不了或跑不了时，在结论里写明「未还原」「子集未验证」。

## 常见误判

| 念头 | 现实 |
|---|---|
| 只改一个字符 | 范围看的是谁的行为变了，不看 diff 行数 |
| 不改的话这个需求会有 bug | 这正是 B 类：把后果讲清楚交给用户定，不替用户定 |
| 是 review agent 提的 | reviewer 判断代码对不对，不判断该不该在这次改 |
| 我之前提过，用户没反对 | 没反对不等于同意 |
| 方案里写了，用户说「开干」 | 用户没有逐项看过的方案不构成授权 |
| 测试全绿、review 通过 | 两者都不检查范围 |
| 顺手格式化一下而已 | 给 owner 增加 review 噪音，也让 blame 失真 |
| 这个问题很严重，必须修 | 越严重越应该让 owner 知道，移交清单就是做这件事的 |
