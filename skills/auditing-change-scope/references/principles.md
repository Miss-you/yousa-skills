# 改动范围审计：原则与出处

## 这是一类什么问题

学名是 scope creep（范围蔓延），落到代码上叫 drive-by change（顺带改动）。更准确的说法是**授权边界漂移**：一次改动的实际范围，超出了提出需求的人明确授权的范围。

它和「代码写得对不对」是两个独立的维度。一处越界改动可以完全正确、有测试、通过 review，仍然不该出现在这次提交里。

### 四种表现

| 表现 | 例子 | 典型来源 |
|---|---|---|
| 改了共享的既有行为 | 把所有数据类型共用的比较逻辑从 `>=` 改成 `>` | 实现时发现它影响新功能 |
| 顺手修无关问题 | 修了别的接口里的空指针 | review 发现、读代码时看到 |
| 外观整理 | 格式化、改名、调注释、补日志字段 | 工具自动、review 建议、「看着不顺眼」 |
| 旋钮和依赖 | 调配置默认值、升级用不到的依赖 | 调试时临时改、没还原 |

### 为什么 AI 更容易犯

1. **优化目标是「系统更正确」，用户要的是「我这件事做完」。** 两者大部分时候重合，不重合的那部分就是越界。
2. **没有归属概念。** 人知道哪些文件是别的组的、改了要打招呼；模型看到的只是一堆可以编辑的文件。
3. **把发现当成了决定。** 发现一个真问题，下一步动作应该是报告，实际做成了修复。
4. **把沉默当成了同意。** 提过一句建议，用户回了别的话题，之后就按「已经说过」处理。
5. **自己给自己定范围。** 把越界的任务写进方案，后续的自审、review、减法检查全都对照这份方案，没有一步回头对用户的原话。
6. **review 是加法。** 每条 finding 都在往 diff 里加东西，没有人检查加进来的东西落在哪。

第 5 条是这个 skill 存在的直接原因，见下面的基线证据。

## 基线证据

写这个 skill 之前做了三组对照测试，每组 3 次，被测 agent 都没有任何范围相关的指导：

| 场景 | 被测 agent 的角色 | 结果 |
|---|---|---|
| 给需求原话和补丁，要求做提交前检查 | 独立检查者 | 3/3 只提交目标内的 3 个文件，拆出 5 个越界文件 |
| 给需求原话和「发现的问题」，要求写方案 | 作者，方案阶段 | 3/3 把共享逻辑的改动列为「需用户决定，默认不做」 |
| 给会话摘要（方案是自己写的、含越界任务、用户未逐项确认），要求做提交前检查 | 作者，提交阶段 | 3/3 判对，并主动指出「用户当时没有同意」 |

9 次没有一次失败。结论：模型不缺判断力，缺的是**被问到**，以及**拿到正确的对照物**（用户原话、谁批准过什么、文件归谁）。真实会话里出事时，这个问题从头到尾没有被问过，而且方案已经被当成了目标。

所以 skill 的形态是输入输出契约，不是禁令清单。

唯一观察到的不稳定：第三组有 1 次在「不归用户的仓库」里提议把顺带修复「单独再提一个 commit」。输出契约里因此加了一条：不归用户的模块，C 类只移交，不主动提议提交。

### 带 skill 的验证

同样用第三组场景，让被测 agent 按 SKILL.md 做：

| 轮次 | 次数 | 分类结果 | 被测 agent 反馈的含糊点 |
|---|---|---|---|
| 初版 | 3 | 3/3 一致：3 个 A、2 个 B、4 个 C；没有再出现「另起 commit」的提议 | 每次 8 至 9 条，集中在：一个改动块混了两类、他人模块里的新增算 A 还是 B、「必需」由谁举证、概括性指令算不算授权、不能还原或不能派 subagent 时怎么办 |
| 修订后 | 2 | 2/2 一致，同上 | 每次 3 至 5 条，均为已处理对但 skill 未明说的细节 |

第二轮反馈对应的补充（B 与 C 按后果落点分界、不归用户时问「要不要找 owner」、输出加授权台账一节等）已写入 SKILL.md，这最后一批措辞没有再做一轮测试。

skill 带来的变化是输出收敛和少量边界判定的统一，不是判断正确率的提升：基线本来就是 9/9。

## 检查原则

| # | 原则 | 判据 |
|---|---|---|
| S1 | 对照物是用户原话 | 目标必须能逐字引用到用户的消息；助手的转述、方案、归纳都不算 |
| S2 | 授权要显式 | 助手提的建议，只有用户之后明确点名同意才算授权 |
| S3 | 一次提交只做一件事 | 每个改动块都能回答「它为这句目标做了什么」 |
| S4 | 行为改动与结构整理分开 | 格式化、改名、重构不和功能改动混在一次提交里 |
| S5 | 改既有行为要升级 | 新增代码默认安全；改变已有调用方行为的改动必须单独拿出来问 |
| S6 | 归属决定谁来定 | 不归用户的模块里，既有逻辑怎么改由 owner 定 |
| S7 | 发现要留痕，不留在 diff 里 | 越界的发现写进移交清单，带证据和建议 |
| S8 | 复核者不看作者的理由 | 给复核者的输入只有台账、归属、补丁 |

## 出处

- **Google Engineering Practices，Small CLs**：一个 CL 只包含一个自洽的改动；重构应与功能改动、bug 修复分开提交；小的清理（如局部变量改名）在不妨碍 review 时可以例外。对应 S3、S4。
  https://google.github.io/eng-practices/review/developer/small-cls.html
- **Linux kernel，Submitting patches**：「Separate your changes」一节要求每个补丁只解决一个逻辑问题，bug 修复和性能改进要拆开；「Select the recipients」一节要求找到子系统的维护者并抄送，改动由维护者把关。对应 S3、S6。
  https://docs.kernel.org/process/submitting-patches.html
- **Kent Beck，Tidy First?**：把结构性改动（不改变行为的整理）和行为改动分到不同的提交或 PR。对应 S4。
  https://henrikwarne.com/2024/01/10/tidy-first/
- **Chesterton's Fence**：不知道一段既有逻辑为什么这样写之前，不要动它。对应 S5、S6。原比较逻辑的注释写着「相等则跳过」，它可能是有意的幂等去重。
- **AI 编码 agent 的越界行为**：一篇执行安全方向的综述在摘要中提到，现实提示下良性但越界的 agent 动作发生率最高可达 17.1%，且现有的访问控制研究没有覆盖这类问题。说明这是 agent 的普遍现象，不是个别会话的偶然。
  https://arxiv.org/abs/2607.05743

## 分类的边界情况

| 情况 | 归类 | 说明 |
|---|---|---|
| 新功能的测试需要一个测试辅助函数 | A | 只服务于目标内的代码 |
| 为了让新代码编译，必须改一个共享接口的签名 | B | 目标必需，但改变了其他实现方 |
| 协议升级到新功能需要的版本 | A | 目标必需，且只改版本号；同时带上的其他依赖升级是 C |
| 新功能用到的既有函数有 bug，不修新功能就不对 | B | 把后果和可选做法讲清楚，由用户或 owner 定 |
| 新功能用不到的既有函数有 bug | C | 移交 |
| 工具对整个文件做了格式化 | C | 还原到只包含自己的改动块 |
| 被改函数里顺手补了一个日志字段 | C | 即使只有一个参数 |
| 用户自己负责的模块里的 C 类 | C | 仍然还原并记录，是否另起一次提交由用户定 |
