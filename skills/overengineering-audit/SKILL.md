# 过度实现审查

## 为什么需要这个 skill

常规 code review 是**加法**的：reviewer 找缺失的校验、缺失的测试、缺失的错误处理，结论总是"再加点什么"。没有任何机制负责反方向。

这不是习惯问题，是认知偏差。Adams 等人 2021 年发表在 Nature 的八组实验证明：**人在改进一个系统时会系统性地忽略"删掉它"这个选项，除非被明确提示去考虑减法**。后续研究发现**大语言模型有同样的偏差，且更强**（见 references/principles.md 的出处）。

所以本 skill 的第一条操作规则就是：**强制提示减法**。对每个发现，必须先问"能不能删"，问过之后才允许问"能不能改小"。

## 何时使用

- 用户说：过度设计、过度实现、是不是太复杂了、简化实现、精简代码、砍一砍、瘦身、over-engineering、simplify
- 功能实现完成后，想确认实现规模是否匹配问题规模
- 常规 code review 之后，补一轮反方向的减法审查

## 硬约束：先锚定目标

**没有目标就没有"必要"可言。** 开始审查前必须先拿到本次改动要解决的问题，按以下顺序找：

1. 用户在当前对话里说的目标
2. spec / 设计文档 / OpenSpec change / 需求文档
3. commit message、PR 描述
4. 都没有 → **停下来问用户**。不要自己猜一个目标然后照着它砍代码

把目标写成一句话，形如「让 X 在 Y 情况下不再发生 Z」。后面每一条质询都对着这句话问：**这段代码是为这句话服务的吗？**

## 审查范围

**默认只审本次变更**：`git diff`（含 staged 与工作区）+ 新增文件。

**未变更代码只在同时满足两个条件时纳入**：
- 问题严重（正确性缺陷、数据竞争、会烧数据的路径），且
- 与本次改动相邻，或被本次改动放大

未变更代码的风格问题、陈旧抽象、"我要是重写会更好"一律**不纳入**。看到了单独记一笔告诉用户，不要顺手改——扩大 diff 本身就是一种过度实现。

**排除**：生成代码（`*_gen*`、`*.pb.go`、`_gen/` 目录、`*.gen.ts`）、vendor、锁文件。

## 九条原则

这些是审查的判据。每条发现都必须能挂到其中至少一条上，挂不上的不是发现，是个人口味。

**判定方法、正反例、代码气味清单、以及每条原则的出处，见 [references/principles.md](references/principles.md)——审查时读它。**

| # | 原则 | 一句话判据 |
|---|---|---|
| P1 | **默认搜索减法** | 每个发现先问「能不能整个删掉」，再问「能不能改小」。顺序不能反 |
| P2 | **YAGNI 与它的边界** | 为假想需求造的能力要砍；让代码更容易读、测、改的投入**不算**过度实现 |
| P3 | **复杂度是难懂难改，不是行数** | 删了行数但让剩下的更晦涩、依赖更多，是净损失 |
| P4 | **重复比错误的抽象便宜** | 只出现两次的相似代码保留重复，第三次再抽象 |
| P5 | **单使用者的间接层是伪装的复杂度** | 只有一个 caller 的 wrapper / 接口 / 策略，内联掉——除非它是真实边界（测试缝、外部依赖、跨进程契约） |
| P6 | **每个旋钮都要有当下的使用者** | 新增的配置项、参数、开关、错误码分支，说不出「现在谁会用另一个值」就硬编码 |
| P7 | **边界情况要能说出触发路径** | 说不出具体触发路径就不处理；说得出但上游已保证不会发生，也不处理 |
| P8 | **每个测试要能说出它防的事故** | 说不出防什么的测试删掉；说得出的用变异验证它真能抓到 |
| P9 | **护栏：不懂就别删，不拿正确性换简洁** | 找不到某段代码存在的理由 = 你还没查清楚，不是它没用 |

## 工作流

### 1. 锚定目标与范围

拿到目标句 + `git diff --stat` 的文件清单。列出本次新增的**构造清单**：新函数、新接口方法、新参数、新字段、新配置项、新错误码、新抽象层、新分支、新测试文件。

这份清单就是审查对象。没进清单的东西不审。

### 2. 逐项质询

对清单里每一项，按 P1 的顺序走：

```
删掉它 → 什么会坏？
  说不出 → 候选：删
  说得出 → 这个"坏"在目标句里吗？
    不在 → 候选：删（记下它为什么在这儿，可能属于别的目标）
    在   → 有没有更小的东西能达到同样效果？
      有 → 候选：简化
      没有 → 保留，并写下理由
```

**必须实际验证「什么会坏」**，不要靠推理：
- 删/改后跑测试与构建，看是否真的红
- 找不到 caller 的东西，用 grep 确认全仓无引用（含测试、配置、生成代码、其它语言的调用方）

### 3. 分级输出

| 级别 | 含义 |
|---|---|
| **必删** | 零使用者、防不可能发生的情况、纯投机 |
| **建议简化** | 有用但过重，存在明显更小的等价做法 |
| **保留（附理由）** | 看着重但确实必要——把理由写下来，这本身就有价值，下一个人不用再问一遍 |

每条给出：`文件:行号`、挂的原则编号、删/简化后**具体什么会变简单**、以及**风险**。

### 4. 修复并验证

按「必删 → 建议简化」顺序改。每改一批就跑全量验证（测试、vet/lint、构建）。

**收敛条件**：改完后总行数应该下降。如果一轮"简化"之后代码变多了，说明走偏了，回退重来。

## 反模式：这些不是过度实现，别砍

砍掉它们会让你显得在简化，实际是在制造事故。审查时逐条排除：

| 不要砍 | 原因 |
|---|---|
| 解释「为什么」的注释 | P3：它降低的是理解成本。只砍复述代码在做什么的注释 |
| 防**外部输入**的校验 | 外部输入不可信，这是必要复杂度。P7 只砍防内部不可能状态的分支 |
| 能说出具体事故的测试 | P8 的判据是「说不出」才删，不是「测试多了就删」 |
| 关键链路的日志与留痕 | 破坏性操作、状态迁移、拒绝路径的留痕是排障的唯一凭据 |
| 为可测试性存在的构造函数 / 接口 | P2 的边界：可测试性投入不算过度实现 |
| 并发保护、幂等保护、终态保护 | 拿正确性换简洁是 P9 明令禁止的 |
| 已上线的对外契约字段 | 删了是破坏性变更，不属于「简化实现」 |
| 不可逆操作（数据迁移、删除）的核对步骤 | 成本不对称，见 references 里 P2 的展开 |

## 输出前的自检

提交结论前逐条确认：

- [ ] 每条发现都挂到了某条原则编号上
- [ ] 每条「必删」都实际验证过零使用者，不是推理出来的
- [ ] 没有一条发现踩到上面的反模式表
- [ ] 未变更代码的发现，确认过「严重且相邻」，否则移出结论、只做提示
- [ ] 改完后跑了全量验证且全绿
- [ ] 净行数下降；没下降就说明这轮没在做减法
