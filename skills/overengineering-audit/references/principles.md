## P1 默认搜索减法

**判据**：对每个新增构造，第一个问题必须是「整个删掉会怎样」，而不是「怎么改得更好」。问过删除之后才允许考虑简化。

**为什么要强制这个顺序**：Adams 等人（Nature, 2021）的八组实验发现，人在被要求改进一个系统时，**几乎不会生成减法方案**——不是生成了然后否决，是根本没想到。只有在任务明确提示"也可以删"时，减法方案才会出现。后续工作发现大语言模型的加法偏差比人更强。

也就是说：一个没有强制减法步骤的 review，无论多认真，产出都会偏向"再加点什么"。顺序本身就是干预。

**气味**：审查结论里全是"建议补充""建议增加""可以考虑加上"，一条删除都没有。这不是代码干净，是审查方法有问题。

**出处**：
- Adams, G. S., Converse, B. A., Hales, A. H., & Klotz, L. E. (2021). *People systematically overlook subtractive changes.* Nature 592, 258–261. https://www.nature.com/articles/s41586-021-03380-y
- *More is More: Addition Bias in Large Language Models.* arXiv:2409.02569. https://arxiv.org/pdf/2409.02569

## P2 YAGNI 与它的边界

**判据**：区分两种"多做的事"：

| 类型 | 处理 |
|---|---|
| 为**假想需求**造的能力（还没有用户、没有 caller、没有需求单） | 砍 |
| 让代码更容易**读 / 测 / 改**的投入 | 不砍 |

Fowler 的原话限定得很清楚：YAGNI 只适用于「为假想特性内建的能力」，**不适用于让软件更容易修改的努力**。这条限定是本原则最容易被误用的地方——拿 YAGNI 去砍可测试性、可读性、可观测性，是曲解。

**四项成本**（Fowler）用来量化投机代码的代价：

- **构建成本**：分析、编码、测试的投入
- **延迟成本**：这段时间本可以做别的功能
- **携带成本**：投机代码留在代码树里，让之后**每一次**改动都更贵——这是最容易被低估的一项
- **修复成本**：需求真来的时候，半年前猜的形状通常对不上，要么重构要么绕开

**不对称性例外**：当「事后补的代价 >> 现在做的代价」时，现在做是对的，不算过度实现。典型：进了主查询路径和联合索引的数据库列（事后要洗数据 + 改全部查询 + 重建索引 + 动接口契约）、不可逆操作前的核对步骤、跨进程的契约字段。判断方法是**算两边的代价**，不是凭感觉说"以后会用到"。

**气味**：
- 只有一个实现的策略模式 / 工厂 / 注册表
- 为"以后可能有第二个"预留的枚举、分支、映射表
- 参数化了但所有 caller 都传同一个值
- 泛型/接口的类型参数只被一种类型实例化

**反例（别砍）**：为了让单元测试能注入依赖而导出的构造函数；把长函数拆开以便阅读；关键链路的日志。这些都落在 Fowler 的限定之外。

**出处**：Martin Fowler, *Yagni* (2015). https://martinfowler.com/bliki/Yagni.html ；*Speculative Generality* 作为代码气味出自 Fowler, *Refactoring*。

## P3 复杂度是难懂难改，不是行数

**判据**：Ousterhout 把复杂度定义为「与系统结构相关的、使系统难以理解和修改的任何东西」，主要来源是两个：

- **依赖**：改一处要跟着改多处（change amplification）、要同时装下很多东西才能读懂（cognitive load）
- **晦涩**：重要信息不显式（unknown unknowns——你不知道自己需要知道什么）

所以行数是**不可靠的代理指标**。一次"简化"如果减了行数但增加了依赖或晦涩程度，是净损失。

**典型的假简化**：
- 把三处显式的条件合并成一个带 flag 参数的函数——行数少了，读的人要在脑子里展开分支
- 用反射/泛型/元编程消掉重复——行数少了，出错时的栈没法看
- 删掉解释"为什么"的注释——行数少了，晦涩度上升
- 把参数塞进 map/context 传递——签名短了，调用方看不出要传什么

**接口深度**：好模块是「简单接口 + 复杂实现」（深模块）。如果一个新增的抽象接口和它的实现一样复杂，它没有隐藏任何复杂度，只是加了一层——按 P5 处理。

**出处**：John Ousterhout, *A Philosophy of Software Design*（复杂度定义、change amplification / cognitive load / unknown unknowns、deep vs shallow modules）。

## P4 重复比错误的抽象便宜

**判据**：**Rule of Three**——第一次直接写，第二次容忍重复，第三次才抽象。只出现两次的相似代码，保留重复。

Metz 描述的失败链条：A 看到重复，抽出来命名；B 遇到一个"几乎符合"的新需求，觉得有义务复用，于是加参数加条件；重复几轮后，这个抽象变成谁都不敢动的条件分支泥潭。**修复错误抽象的代价，远高于当初保留重复的代价。**

**判定要点**：看两段代码是否会**因为同一个原因**一起改变。形状相似但变化原因不同的代码，不是重复，是巧合。

**气味**：
- 抽出来的公共函数带 `isXxx bool` / `mode string` 参数，函数体里靠它分叉
- 抽象只服务两个 caller，且两个 caller 传的参数几乎互补
- 为了复用而把两个不同领域的概念塞进同一个类型

**反例（别砍）**：真正会同因同变的重复（比如同一个业务规则在三处各写一遍），抽象是对的。

**出处**：Sandi Metz, *The Wrong Abstraction* (2016). https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction ；Rule of Three 见 Fowler, *Refactoring*。

## P5 单使用者的间接层是伪装的复杂度

**判据**：一个 wrapper / 接口 / helper / 中间类型，如果只有一个 caller 或只有一个实现，默认内联掉。

**豁免**（这些单实现是合理的）：
- **测试缝**：为注入内存数据库、fake 外部服务而存在的构造函数或接口
- **外部边界**：包装第三方 SDK、跨进程 RPC、数据库访问——它们隔离的是你控制不了的东西
- **跨进程契约**：proto / API schema，实现方只有一个但契约本身有独立价值

**为什么这条重要**：单 caller 的包装函数会污染 panic 栈和调用链——排障时你多跳一层才看到真实逻辑，而这一层什么都没做。

**气味**：
- `func doXxx() { return doXxxImpl() }`
- 只有一个方法、一个实现、且实现里只有一行的接口
- 为了"以后可能换实现"而建的接口，但换实现的需求不存在

**出处**：Ousterhout 的 shallow module（接口复杂度接近实现复杂度，没有隐藏任何东西）；与 P2 的 speculative generality 同源。

## P6 每个旋钮都要有当下的使用者

**判据**：每新增一个配置项、函数参数、feature flag、错误码分支，必须能回答：**现在谁会给它传另一个值？** 答不上就硬编码成常量。

旋钮的成本不是定义它的那一行，是：文档要写、测试要覆盖组合、排障时要先确认它的取值、以及它会长期停在默认值上没人敢动。

**特别检查**：
- 配置项：yaml 里加了但三个环境都填一样的值 → 硬编码
- 函数参数：所有 caller 传同一个字面量 → 去掉参数
- 错误码：调用方对两个码的处理完全一样 → 合并成一个
- 开关：加了但没有关掉它的预案和触发条件 → 不是逃生开关，是死代码

**反例（别砍）**：真的有两个环境/两个调用方取不同值的配置；有明确回滚预案的逃生开关。

## P7 边界情况要能说出触发路径

**判据**：处理一个边界情况前，必须能说出**具体的触发路径**——什么输入、经过哪个调用方、到达这里。

两种要砍的情况：
1. **说不出触发路径**：纯想象的输入
2. **说得出但上游已保证不会发生**：调用方已经校验过 / 类型系统已经排除 / 数据库约束已经保证

第 2 种尤其常见，且危害不只是冗余：它让读代码的人以为这个状态**可能**发生，从而在别处也加防御，复杂度扩散。

**关键区分**：

| 输入来源 | 处理 |
|---|---|
| 外部（用户请求、外部服务响应、配置文件、DB 里的历史数据） | **必须校验**，这是必要复杂度 |
| 内部（同进程的调用方刚构造的对象、刚校验过的参数） | 不防。要防就用类型/断言表达不变量，不要用 if 悄悄兜底 |

**气味**：
- nil 检查加在一个刚被 `new` 出来的对象上
- 同一个字段在三层各校验一次
- `default:` 分支处理一个穷尽的 enum
- 兜底逻辑把一个"不该发生"的状态悄悄修正，导致真出问题时无声无息

## P8 每个测试要能说出它防的事故

**判据**：对每个测试用例问：**它防的是哪个具体事故？** 用一句话写出来（"两个业务、相同 userId，任务串号下发到错误的客户端"）。写不出来的删掉。

写得出来的，再做**变异验证**：把被测的那行逻辑改坏（删掉条件、反转比较、去掉过滤），确认测试真的变红。变异不红的测试是假绿——它占着维护成本但不提供任何保护。

**要砍的测试**：
- 测语言/框架行为的（测 getter 返回刚 set 的值、测 ORM 会写入数据库）
- 断言了实现细节而非行为的（断言内部调用了哪个方法几次）
- 用 mock 测 mock 的（整条链路都是桩，实际上什么都没验证）
- 同一条路径的近似重复用例（参数换个值，走的是同一个分支）

**不要砍**：能说出具体事故、且变异验证通过的用例——哪怕它看起来简单。

## P9 护栏：不懂就别删，不拿正确性换简洁

**判据**（Chesterton's Fence）：找不到某段代码存在的理由，**结论是"我还没查清楚"，不是"它没用"**。删除前必须先查：git blame、关联 commit/issue、注释、测试。

查完仍然找不到理由，且确认零使用者，才可以删——并在结论里注明"查过 X、Y、Z 均未发现用途"。

**绝对不能以简化为名删掉的**：
- 并发保护（锁、原子操作、事务边界）
- 幂等保护、终态保护、重复提交保护
- 权限与归属校验
- 数据迁移/删除操作前的核对
- 审计与破坏性操作的留痕

这些的共同点是：**删掉之后测试大概率仍然是绿的**，问题只在生产的并发/异常路径上显现。测试绿不是删除它们的许可。

**自检**：如果一条"简化"建议的收益是"少几行"，而风险是"某种情况下数据不对"，这条建议不成立。

**出处**：Chesterton's Fence 出自 G. K. Chesterton, *The Thing* (1929)。
