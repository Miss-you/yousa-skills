# Go 可读性打磨

## Overview

功能完成、review 通过之后、提交之前跑一次。只问一个问题：**读者要在脑子里多做什么，才能确认这段代码在干什么。** 把那些「多做的事」去掉。

行为不变、测试前后都绿、独立 commit。这三条是它能放心跑的前提，也是「改了 reviewer 要重看」这个反对意见的答案：reviewer 只需看一个不改行为的小 diff。

跟别的 review skill 的分工：减法（overengineering-audit、auditing-code-comments）先跑，可读性再跑，3am 最后。减法砍东西，这里有时会加一个 helper，顺序不能反。

## When to Use

- 提交前，对本次 `git diff` 做一遍
- 用户点名「梳理 / 理顺」某个函数：范围就是那个函数，不看 diff
- 不适用：代码还在改、测试没绿、用户要的是找 bug 或提性能

## 流程

1. **定范围**：默认只看本次 diff 里的函数；未改动的老代码不碰，除非用户点名。
2. **找停顿点**：通读一遍，标出每个「读者得回头看 / 得自己推一遍才能确认」的位置。只记位置和原因，先不想改法。
3. **对照 mindset 表分类**，按阅读成本排序，**最多取 3 处**。改动总量不超过原函数长度。
4. **改**：行为不变；不动被改函数的签名（测试可能用 mockey 之类的工具按符号 mock 整个函数）；`gofmt`；跑原有测试，不改测试断言（改了说明行为变了，停下来）。
5. **非可读性的发现转出去**：bug、日志缺失、性能、redis.Nil 区分之类，一律写进汇报的「另行处理」段，不在这个 pass 里改。
6. **汇报**：每处改动一句「读者原来要做什么 → 现在不用了」；重构过程中**浮出来的隐藏分支**（原来看不见的语义）单独列出，交给用户确认是不是有意的，不擅自改。

## Mindset 表

每条一个「味道」，例子见 [references/examples.md](references/examples.md)。

| # | 原则 | 味道 | 改法 |
|---|------|------|------|
| 1 | 主函数是一条直线 | 两条路径为共用一个 return 在中途汇流；变量的来源要回头看 | 分支推进 helper，主函数只剩步骤 1/2/3 |
| 2 | 数据不往返 | 同一函数里拼字符串再解析回来、序列化再反序列化 | 拆开出口，各自直接 return |
| 3 | helper 说「是什么」不说「怎么做」 | 调用方得知道格式、空值约定才能用 | 返回 `(v, ok)`，把格式和约定藏进去 |
| 4 | 相同的长得一样，不同的看得出来 | 两段逻辑一样但写法不同；或两个分支看似能合并但业务上有差 | 前者统一写法；后者故意分开并加一句为什么 |
| 5 | 守卫前置 | 正常流程缩在两层 if 里面 | 早返回，主路径靠左 |
| 6 | 按变更原因抽取 | 三处同样的赋值，改一处必改另两处 | 抽一个小函数；只是文本像但会因不同原因改的，不抽 |
| 7 | 名字代替魔数 | `case 1: / case 2:` 靠注释解释 | 先 grep 已有常量再用；没有的不新加 |
| 8 | 读者是六个月后的自己 | 不看别的文件读不懂这个函数 | 缺的上下文用一行路标注释补，不复述代码 |

## 门槛

- **抽 helper 的标准是「它藏住了什么」**，不是行数。只把三行换个名字、接口和实现一样宽的，不抽——那是 3am skill 说的 mock-only 间接层。
- **加常量的标准是「消除一处重复的事实」**（同一格式串写两遍）。只是给一个数字起名字、用一次，不加。
- **改动量**：≤3 处、diff 不超过原函数长度。超了说明该拆成两轮，或者这不是可读性问题而是设计问题。

## 红线

| 念头 | 现实 |
|------|------|
| 「都能读懂，一行别动」 | 「能读懂」的代价是读者推一遍。你推的那一遍就是要去掉的成本 |
| 「改了 reviewer 要重看」 | 行为不变 + 测试绿 + 独立 commit，reviewer 看的是十行 diff |
| 「顺便把常量、算式、闭包都整理了」 | 九处改动 = 重写。挑成本最高的 3 处，其余记下来下轮 |
| 「顺便把 redis.Nil 区分一下」 | 那是行为改动，转到「另行处理」 |
| 「重构时发现这个分支好像不对，改掉」 | 浮出来的语义要上报，不能在可读性 pass 里改 |
| 「抽个 helper 主函数就短了」 | 短不是目标。helper 没藏住东西，读者还得跳进去 |
