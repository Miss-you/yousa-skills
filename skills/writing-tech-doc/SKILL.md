# 写中文后台技术文档

<!-- doc-lint:disable 标题 数据口径 -->
<!-- 本文是 skill 说明而非交付文档，章节编号与口径声明的规则不适用。 -->

分三轮，不要一次写完就交付。第一轮解决「写什么」，第二轮解决「怎么组织」，第三轮解决「怎么说」。一次性追求三者会写成博客体。

## 轮次一：内容草稿

先把事实和数据落到文件里，此时不追求措辞和排版。

1. 确认文档类型（问题分析 / 故障复盘 / 技术方案），据此选骨架，见 [references/structure.md](references/structure.md) 的「骨架」。
2. 结论前置。第 1 节写结论和影响面，读者看完前 20 行就能决策。
3. 所有数字标注来源和口径。没有口径的数字等于没写。
4. 代码位置写到 `文件:行号`，便于点击跳转。

写完存盘再进入轮次二，不要边写边改文风。

## 轮次二：结构与资产

对着 [references/structure.md](references/structure.md) 逐项补齐，然后跑 lint。

补齐项：

- 首部元信息表（环境 / 服务 / 接口 / 数据窗口）
- 二级标题改成 `N.` 编号，三级 `N.M`
- 映射关系、多维对比、时间序列事件改成表格
- 分支流程补 mermaid（能三行文字讲清的不画）
- 数据章节开头补口径声明
- 超过 10 行的清单下沉到附录

跑检查：

```bash
python3 <skill-dir>/scripts/doc_lint.py <file.md>   # <skill-dir> 为本 skill 的安装目录
```

覆盖文风红线、标题形态、表格列数与表头、mermaid 语法、数据口径、段落密度。error 必须清零，warn 逐条判断后再决定是否保留。

mermaid 节点标签含 `()` `:` `/` 时不加引号会渲染失败，lint 报 error，按提示加引号。

## 轮次三：文风修正

对着 [references/style.md](references/style.md) 通读一遍，重点改三处：

| 检查点 | 判断标准 |
|---|---|
| 标题 | 是在命名内容，还是在讲「我发现了什么」？后者改成名词短语 |
| 判定句 | 有没有情绪词和替读者总结？改成「数据 + 判定」 |
| 加粗 | 正文有加粗就删，层级和表格已经够分主次 |

`references/style.md` 的「标题改写对照」和「正文改写对照」可直接作为改写参照。

改完再跑一次 lint，确认 0 error。

## 交付前

- 数据核对：文中所有百分比和计数能否从声明的口径重新推出
- 跨章引用用编号（「见 7.1」），不用「见前面那节」
- 进仓库前跑 secret-scan，尤其是含 URL、ID、日志片段的分析类文档
- 需要逐字校对错别字和标点时，可再配合 zh-proofreading

## 复发与增补

同一问题再次发生时，追加新章节记录新窗口的数据，不改写历史章节的结论。若新数据推翻旧结论，在旧结论处标注「见第 N 节，该结论已调整」，保留推翻的过程，读者需要知道判断是怎么变的。

## 常见错误（Common mistakes）

| 错误 | 改法 |
|---|---|
| 三轮合并成一轮，边写内容边抠文风 | 先存盘内容草稿，再分轮处理结构和文风 |
| 数字没有口径，评审时被逐条追问 | 数据章节开头声明来源、时间窗口、统计对象、是否全量 |
| 标题写成发现或结论，如「缺陷一直在，只是没人看见」 | 改为名词短语，如「3.1 基线对比」 |
| 能三行讲清的流程也画 mermaid | 只为分支、并发、跨服务时序画图 |
| mermaid 节点标签含括号不加引号，渲染失败 | 按 lint 提示给标签加双引号 |
| 复发时改写历史章节的结论 | 追加新章节，旧结论处标注已调整并指向新章节 |
| lint 的 warn 全部机械清零 | warn 逐条判断，确有必要的表述可以保留 |
| 文档里残留真实账号、内部域名、日志原文 | 交付前脱敏，并跑 secret-scan |
