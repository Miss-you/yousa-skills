## 目标口吻

普通后台工程师写给同事看的内部文档。平铺直叙，数据和表格说话，不替读者下判断。

反面参照是「AI 味」：叙事化标题、层层铺垫、情绪副词、密集加粗、破折号补充。这些让文档读起来像博客而不像技术材料。

## 禁用句式

`doc_lint.py` 会扫这些，命中即 error 或 warn。

| 类型 | 禁用 | 改法 |
|---|---|---|
| 对比强调 | 不是 A 而是 B | 直接陈述 B，或用表格列 A / B |
| 主观强调 | 主要是、主要来自、主要原因 | 给具体数字：「100 条中 80 条来自 X」 |
| 补充句 | 即：xxx、注：xxx | 并入上一句，或单独成句 |
| 评价性副词 | 非常、极其、惊人、显然、其实 | 删除。程度靠数据体现 |
| 替读者总结 | 简单来说、换句话说、综上所述、由此可见 | 删除。结论直接写 |
| 情绪化引导 | 值得注意的是、有意思的是、最重要的是 | 删除。重要的内容靠位置和层级体现 |
| 破折号铺陈 | `A —— B` | 拆成两句，或改冒号 |
| 箭头串联 | 正文里 `A → B → C` | 改文字叙述、表格或 mermaid（代码块内的调用链除外） |

## 标题改写对照

以一次虚构的「订单回调重试风暴」复盘为例：

| 改前 | 改后 |
|---|---|
| 一、机制缺陷：回调早到时不写幂等记录 | 2. 缺陷分析 |
| 缺陷一直在，D 日才被看见 | 3.1 基线对比 |
| 为什么基线量一直没人上报：失败是静默的 | 2.6 失败的静默性 |
| 模板 A 把两波请求串成了一伙 | 并入 4.2 结果，用一句判定收尾 |
| 打法变了：先下一笔单再批量下单 | 5.4 触发方式 |
| 同一个脚本，10 个下单账号 | 5.2 汇总指标 |
| 模板：模板 B 仍在用，新增 1 个 | 5.6 请求模板变化 |
| 三个发现 / 三个注意事项 | 按内容命名，或直接用表格承载 |
| 我们提供不了、需要网关侧补的部分 | 7.6 待网关侧补充 |

规律：改前的标题在讲「我发现了什么」，改后的标题在讲「这一节是什么」。数数式标题（三个发现、五个要点）一律换成内容命名。

## 正文改写对照

| 改前 | 改后 |
|---|---|
| 报文长度一模一样而字段不同，不可能是巧合，是同一模板做了微小改动 | 判定为同一请求模板的微改版本（修改时间戳或替换单个字段） |
| 两列几乎完全同步，不是系统抖动 | 失败率与批量账号占比同步变化，非系统抖动 |
| 同一个脚本，换号换商品，模板没换 | 结合两时段账号交集为 0、商品 ID 交集为 0，可判定两批请求同源 |
| 差别不在于账号本身，而在于批量账号下的全是新用户 | 差异来源是批量账号的请求全部来自新注册用户 |
| 09:00 时段的 100% 失败主要来自 user_A | 09:00 时段的 100% 失败中，100 条有 80 条来自 user_A |

规律：把「我的解读」换成「数据 + 判定」。判定可以下，但要紧跟依据，且不带情绪词。

## 加粗与强调

正文不加粗。层级、表格、位置已经足够分主次，加粗只会稀释。

例外：

- 表格单元格内标注关键值
- 行内代码用反引号，不用加粗

结论章节也不加粗。用编号列表：

```markdown
### 1.1 结论

1. 支付回调先于订单落库到达时，处理分支提前返回且不写幂等记录，网关按失败持续重试。
2. D 日的重试量由批量下单脚本触发，较日常基线放大数十倍。
3. D+1 日脚本改为先单笔后批量，缺陷命中率由约 70% 降至约 20%。
```

## 人称

技术文档不出现「我们」「我」「你」。

| 改前 | 改后 |
|---|---|
| 我们提供不了的部分 | 待网关侧补充 |
| 我查到凌晨和下午的账号交集为 0 | 两时段账号交集为 0 |
| 你可以按请求模板归并账号 | 可按请求模板归并账号 |

例外：给下游团队的交付章节可以用「需 xx 侧确认」这类指向明确的表述。
