# Spec-to-TechDoc：变更驱动的技术文档生成

## 概述

把"一次变更"——规格产物 + 代码 diff——整理成一份给两类读者看的技术方案：客户端开发拿去对接接口，后台开发 / 测试 / 运维拿去看决策、测试覆盖和上线依赖。文档章节按实际变更动态裁剪，不套固定模板。

[OpenSpec](https://github.com/Fission-AI/OpenSpec) 是一个公开的规格驱动开发工具；本 skill 优先读取它的 change 产物，但**不依赖它**——没有 OpenSpec 时走手动模式，从 git diff / commit 历史推断变更范围。

## 适用场景

- 一次 spec 变更（OpenSpec change 或任意需求）开发完成，需要输出技术方案 / 接口文档
- 用户说"输出技术方案""写技术文档""生成接口文档""把这次改动归档成文档"
- 需要给客户端同学一份可以直接对照开发的接口说明

不适用：从零写设计提案（还没有代码）、只想润色已有文档。

## 输入

用户指定一个 OpenSpec change 名称，或手动描述变更范围。可选参数：
- `--change <name>` — OpenSpec change 名称
- `--ticket <id> <desc>` — 需求单 ID 与简述（任意需求管理系统均可）
- `--output <path>` — 输出文件路径（默认 `docs/<需求简称>-技术方案.md`，项目有约定时按项目约定）

## 工作流程

### Step 1: 收集变更产物 & 确定范围

**OpenSpec 模式**（有 change）：
```bash
openspec status --change "<name>" --json
openspec instructions apply --change "<name>" --json
```
读取 `contextFiles` 中所有产物：proposal.md、design.md、tasks.md、delta specs。

**手动模式**（无 OpenSpec / 无 change）：

1. 从用户描述中提取：需求单 ID、变更范围、涉及服务
2. 用 `git diff --name-only <base>..HEAD` 获取变更文件列表
3. 用 `git log --oneline <base>..HEAD` 获取 commit 历史
4. 从变更文件列表推断涉及的架构层次（IDL / DAO / Logic / API / 测试 / 配置）
5. 确定版本号（从 commit message、用户描述或项目常量文件中的版本常量推断）

### Step 2: 判定文档规模 & 智能收集

#### 2.1 文档规模分级

根据变更范围自动选择文档规模：

| 规模 | 条件 | 产出 |
|------|------|------|
| **轻量级** | 修改文件 ≤5，单接口变更 | 需求概述 + 接口文档 + 修改文件清单（1-2 页） |
| **标准级** | 修改文件 6-15，多接口变更 | 全部适用章节（3-5 页） |
| **重量级** | 修改文件 >15，跨服务/全链路 | 全部适用章节 + 架构总览，可拆分子文档 |

#### 2.2 章节选择规则

根据实际变更内容动态决定包含哪些章节，而非套用固定模板：

| 章节 | 触发条件 |
|------|---------|
| 需求概述 | 始终包含 |
| 客户端接口文档 | IDL（proto 等）有 RPC/message 变更，且客户端可见 |
| 关键技术决策 | design.md 有 alternatives，或 review 中有争议点 |
| 单元测试清单 | 存在新增/修改的测试文件（如 `*_test.go`） |
| 配置与上线依赖 | 涉及功能开关/业务配置、搜索索引 mapping、缓存 key、版本号变更 |
| 未完成待办 | tasks.md 中有 status!=done 的条目 |
| 修改文件清单 | 始终包含 |
| 架构总览 | 变更跨 ≥3 层（IDL/DAO/Logic/API） |

**空章节直接省略，不要用"暂无"占位。**

#### 2.3 智能收集

先用 Glob 快速扫描变更文件列表，判断涉及哪些维度，然后**按需**启动并行 agent（Task tool, subagent_type=Explore），最多 3 个：

| 条件 | 启动的 Agent | 收集内容 |
|------|-------------|---------|
| 有 `.proto` / IDL 变更 | **IDL + 接口 Agent** | 新增/修改的 message、enum、RPC 定义；完整 Req/Rsp message（全量字段）；接口路由路径（如 proto 的 `google.api.http` 注解或路由表）；新增错误码；版本常量 |
| 有测试文件变更 | **测试 Agent** | 测试函数名、文件路径+行号、覆盖场景（从函数名和首个 assertion 推断） |
| 有业务配置 / 常量 / 缓存 key / 索引 mapping 变更 | **配置 Agent** | 功能开关与业务配置、索引 mapping 变更、缓存 key 变更、UI/展示配置变化、需 DBA/运维手动执行的操作 |
| 有业务逻辑变更但无上述任一条件 | **逻辑变更 Agent** | 核心算法/业务流程变更、关键函数签名变化 |

**文件搜索策略**（使用搜索模式，而非硬编码路径；按项目实际布局调整）：
- 错误码：搜索 `**/errcode/*` 或 `**/errs/*` 中的常量定义
- 版本常量：搜索常量文件，如 `**/constant*.*`
- 缓存 key：搜索常量文件或缓存模块中的 key 定义（如 `*_KEY` / `*Key` 前缀的常量）
- 功能开关 / 业务配置：搜索 `**/*config*`、`**/*conf*` 及配置中心相关代码

### Step 3: 生成文档

按照 [references/doc-template.md](references/doc-template.md) 的格式规范生成文档。

**核心原则**：
- 只生成 Step 2.2 中触发的章节，跳过未触发的章节
- 章节编号连续（不因跳过章节出现断号）
- 文档规模匹配 Step 2.1 的分级
- 接口文档：每个接口一个独立小节，铺开写，不要用汇总表替代
- 技术决策：从 design.md 提取 + 补充 review 阶段的决策
- 测试清单：按文件分组，表格列出函数名和覆盖场景
- 配置依赖：区分"上线前必须完成"和"上线后按需操作"

### Step 4: 用户确认

输出文件路径和章节概要，等待反馈迭代。

## 接口文档格式规范

详见 [references/doc-template.md](references/doc-template.md) 的「客户端接口文档」节。核心要点：

**每个接口独立成节**，按变更类型选择合适的格式：

**新增接口** — 完整展示请求参数表格 + 响应 protobuf 定义 + 错误码。示例：

```markdown
### X.Y 接口中文名

**接口路径**: `/service/module/action`
**说明**: 一句话说明用途和触发场景。

**请求参数**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | int64 | 是 | 用户ID |

**响应参数**:

（protobuf message 定义块）
```

**已有接口新增字段** — 新增字段**加粗**，被替代的旧字段用 ~~删除线~~ 标注。请求新增时列全量请求表格；仅响应新增时用 `// ... 已有字段不变 ...` 省略旧字段。

**附加小节**（按需）：
- 关键字段结构：多个接口共用的 enum、子 message 集中定义一次
- 关键错误码：表格列出错误码名、值、触发场景、客户端处理
- 客户端适配要点：编号列表
- 接口无变更确认：仅在变更涉及 ≥3 个相关接口时才列出，用表格说明哪些接口未受影响

## 示例

**OpenSpec 模式**：

> 用户：给 `add-order-tags` 这个 change 输出技术方案
>
> → 读取 change 的 proposal/design/tasks/specs → 变更 9 个文件、2 个接口 → 标准级 → 启动 IDL + 测试两个 agent → 生成「需求概述 / 客户端接口文档 / 关键技术决策 / 单元测试清单 / 修改文件清单」，跳过无触发的配置与架构章节 → 输出路径 + 章节概要，等用户反馈。

**手动模式**（无 OpenSpec）：

> 用户：基于 main..HEAD 的改动写一份接口文档，需求单 1024 订单列表支持标签筛选
>
> → `git diff --name-only main..HEAD` 只动了 3 个文件、1 个接口 → 轻量级 → 只生成需求概述 + 接口文档 + 修改文件清单。

## 写作原则

1. **接口文档给客户端看**：铺开写，每个接口独立，不要让客户端自己拼凑
2. **技术决策给后台看**：记录"为什么"而不仅是"做了什么"
3. **测试清单给测试/review 看**：函数名 + 覆盖场景，一目了然
4. **配置依赖给运维/DBA 看**：可执行的命令，明确的时序
5. **语言跟随项目**：默认中文，与项目已有文档保持一致
6. **聚焦变更**：只记录本次变更涉及的内容，不复述已有功能
7. **代码引用**：proto 用代码块，不要用散文描述字段

## 常见错误

- 用汇总表替代接口详情（客户端看不懂）
- 复述已有功能的工作原理（应聚焦变更增量）
- 用散文描述 proto 字段（应用代码块）
- 空章节占位（"暂无" → 直接省略该章节）
- 跳过章节后编号断号（应重新连续编号）
- 测试清单只列函数名不写覆盖场景（失去价值）
- 文档里残留硬编码版本号或 `XXXX` 之类的模板值（用 `V{version}` 或实际常量值替换）
- 小改动套用重量级结构（应按 Step 2.1 分级裁剪）
- 配置依赖不区分上线前/上线后，或只写描述不给可执行命令
