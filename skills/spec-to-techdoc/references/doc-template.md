# 技术方案文档模板

文档默认输出到 `docs/<需求简称>-技术方案.md`，项目有约定时按项目约定。

> **重要**：本模板定义了所有可选章节。生成文档时，只包含 SKILL.md Step 2.2 中触发的章节，
> 章节编号保持连续（不因跳过而断号）。空章节直接省略，不要用"暂无"占位。

## 文档头

```markdown
# <需求简称> — 技术方案

> 需求单: <ID>
> 状态: 已完成（N/M tasks）
> 最后更新: YYYY-MM-DD

---
```

---

## 需求概述（始终包含）

3-5 行说清楚做了什么。包含：
- 核心变更是什么（如"从单选变为多选"）
- 涉及哪些关键改动点（用列表）
- 改造范围一句话（如"IDL → DAO → Logic → API 全链路"）

---

## 客户端接口文档（IDL 有客户端可见的 RPC/message 变更时包含）

**核心原则**：每个接口一个独立小节，不要用汇总表替代。

### 接口格式

按变更类型选择合适的格式。以下是三种典型场景的示例：

#### 示例 1：新增接口

```markdown
### X.Y 获取订单列表

**接口路径**: `/order/list`

**说明**: 分页获取当前用户的订单列表，客户端进入"我的订单"页时调用。

**请求参数**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | int64 | 是 | 用户ID |
| cursor | string | 否 | 翻页游标，首页为空 |
| pageSize | int32 | 否 | 每页数量，默认20 |

**响应参数**:

\`\`\`protobuf
message ListOrdersRsp {
    int32 code = 1;                    // 返回码
    repeated OrderItem orders = 2;     // 订单列表
    bool hasMore = 3;                  // 是否有更多
}
\`\`\`

**错误码**: `ParamError` — userId 为空
```

#### 示例 2：已有接口，请求新增字段

对于创建/编辑类接口，列出**全量请求参数表格**，本次新增字段**加粗**，被替代的旧字段用 ~~删除线~~ 标注。

```markdown
### X.Y 新建收货地址

**接口路径**: `/address/create`

**说明**: 已有接口，本次新增地址标签列表字段，替代旧的单个标签字段。

**请求参数**:

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userId | int64 | 是 | 用户ID |
| ~~tag~~ | ~~int32~~ | ~~否~~ | ~~旧地址标签，V{version} 不再使用~~ |
| **tags** | **repeated int32** | **是** | **地址标签列表（多选）** |
```

#### 示例 3：已有接口，仅响应新增字段

对于查询/列表类接口，不列全量字段，只展示新增部分。

```markdown
### X.Y 获取收货地址详情

**接口路径**: `/address/detail`

**说明**: 已有接口，本次响应新增配送时效字段。

**本次响应新增字段**:

\`\`\`protobuf
message GetAddressDetailRsp {
    // ... 已有字段 1-N 不变 ...

    // V{version} 新增
    int32 deliveryDays = N+1;  // 预计配送天数
}
\`\`\`
```

### 接口文档附加小节（按需）

以下小节根据实际情况选择性包含：

**关键字段结构** — 多个接口共用的 enum、子 message 集中定义一次：

```markdown
### X.Y 关键字段结构

\`\`\`protobuf
enum AddressTag {
    ADDRESS_TAG_UNKNOWN = 0;
    ADDRESS_TAG_HOME = 1;
    ADDRESS_TAG_OFFICE = 2;
}
\`\`\`
```

**关键错误码** — 表格列出：

```markdown
### X.Y 关键错误码

| 错误码 | 值 | 触发场景 | 客户端处理 |
|--------|-----|---------|-----------|
| `TagsEmpty` | 40012 | 未选择地址标签 | toast 提示 |
```

**客户端适配要点** — 编号列表，包含版本判断逻辑：

```markdown
### X.Y 客户端适配要点

1. **多选替代单选**：V{version} 起 tag 字段废弃，使用 tags
2. **版本判断**：按客户端版本做兼容判断（如有），写清判断字段和阈值常量
```

**接口无变更确认** — 仅在变更涉及 ≥3 个相关接口时包含，用表格说明未受影响的接口：

```markdown
### X.Y 接口无变更（确认）

以下相关接口本次无任何变更，旧客户端行为不受影响：

| 接口 | 路径 | 说明 |
|------|------|------|
| 获取默认地址 | `/address/default` | 无变更 |
```

## 关键技术决策（design.md 有 alternatives 或 review 有争议点时包含）

### 设计阶段决策

每个决策用以下结构：

```markdown
### DX: 决策标题

**决策**：一句话说明选择了什么方案。

**否决方案**：
- 方案 A → 为什么不行
- 方案 B → 为什么不行

**理由**：为什么选择当前方案。
```

如果决策涉及算法或映射规则，用代码块或表格说明。

### Review 阶段决策

用表格记录 review 过程中的决策点：

```markdown
### DX: Review 阶段决策

| 决策点 | 结论 | 原因 |
|--------|------|------|
| 函数 A 的实现方式 | 采用方案 X | 理由 |
```

## 单元测试清单（存在新增/修改的测试文件时包含）

按文件分组，每个文件一个子节。

```markdown
### X.Y 分类名

**文件**: `path/to/file_test.go`（N 个测试函数）

| 测试函数 | 覆盖场景 |
|---------|---------|
| `TestXxx` | 一句话说明 |
| `TestYyy` | 一句话说明 |
```

末尾加一个统计表：

```markdown
### X.Y 测试统计

| 类别 | 数量 |
|------|------|
| 分类 A | N |
| 分类 B | M |
| **合计** | **总数** |
```

## 关键配置与上线依赖（涉及功能开关/业务配置、索引 mapping、缓存 key、版本号变更时包含）

分"上线前必须完成"和"上线后按需"两类。

典型子节（按需选取）：

### 需手动执行的操作（如 ES Mapping）

说明操作内容 + 提供可执行的命令/语句 + 强调时序（必须在代码上线前/后）。

### 业务配置开关

表格列出：配置项、Key、默认值、说明。附切换步骤。

### 版本号常量

列出常量名、值、含义。

### 无需额外操作的部分

明确列出哪些不需要操作（如 schemaless 存储无需 migration）。

## 未完成待办（tasks.md 有 status!=done 条目时包含）

按优先级列出：
- stub 实现（后续独立任务）
- 需要单独 PR 的改进
- 测试补充建议

## 写作原则

1. **接口文档给客户端看**：铺开写，每个接口独立，不要让客户端自己拼凑
2. **技术决策给后台看**：记录"为什么"而不仅是"做了什么"
3. **测试清单给测试/review 看**：函数名 + 覆盖场景，一目了然
4. **配置依赖给运维/DBA 看**：可执行的命令，明确的时序
5. **语言跟随项目**：默认中文，与项目已有文档保持一致
6. **聚焦变更**：只记录本次变更涉及的内容，不复述已有功能
7. **代码引用**：proto 用代码块，不要用散文描述字段

## 反模式（避免）

- 用汇总表替代接口详情（客户端看不懂）
- 复述已有功能的工作原理（聚焦变更增量）
- 用散文描述 proto 字段（应用代码块）
- 空章节占位（"暂无" → 直接省略该章节）
- 测试清单只列函数名不写覆盖场景（失去价值）
- 模板中出现硬编码版本号（用 `V{version}`、实际常量值替换）
