# 先定约束，再出方案

## 为什么需要它

方案被推翻重来，多数时候不是「想错了」，而是**每一轮都在用一个没说出口、且不断变化的权重函数**。而权重本该是输入。

真实案例：同一个「列表接口字段与检索结果不一致」的问题，方案在四轮里变了三次——先按「长期可维护性」提合并重构，再按「改动最小」退成局部补丁，又按「可维护性」提到删除旧结构，最后才拿到真实约束（未上线、项目晚期、公共模块不能动）推倒重来。三轮全是在错误约束下做的局部最优。

**代码里读不到项目阶段，也读不到「这块是谁的地盘」。** 这类约束存在人的脑子里、事故复盘里、发布节奏里。不主动确认就等于猜。

## 何时使用

- 用户问「该怎么改」「出个方案」「要不要重构」
- 准备提出任何涉及新增/修改/删除结构的技术方案
- 已经写完代码，但要回答「后面怎么演进」

**不适用**：单点 bug 修复、用户已明确给出改法、纯查询类问题。

## 四问清单

出方案前必须有答案。**先自查再问——但自查是为了把问题问准，不是为了不问。**

- 自查能拿到**事实**：上线没有、几个调用方、什么时候引入的
- 自查拿不到**意图**：要不要保兼容、这个模块这次能不能动、还剩多少时间

两者之间没有蕴含关系。「配置开关没配」是事实，「所以可以大改」是意图——中间隔着一个只有用户知道的判断。

**对任何一问的答案不确定，就必须在出方案之前问清楚。** 拿推测当约束，代价是整个方案推倒重来，比多问一句贵得多。

### 1. 可逆性：这段代码上线了吗？谁在依赖？

决定兼容性的权重。这是 Kent Beck 的判据：**结构变更可逆，行为变更不可逆**。

| 状态 | 门的类型 | 该怎么权衡 |
|---|---|---|
| 未上线 / 开关未开 | two-way door | **大胆往可维护性靠**。别为想象中的存量依赖打补丁 |
| 已上线、有客户端依赖 | one-way door | 兼容优先，加 v2 而不是原地改 |

**自查方式**（做完这些还不确定才问）：
- `git log --format="%ad %s" --date=short -1 -S "<关键符号>"` 看引入时间
- 查配置中心对应开关是否开启
- 查网关是否已注册路由
- grep 调用方数量

### 2. 阶段：项目现在处在什么节点？

**这个通常必须问。** 早期立项 vs 临近发版，决定「重构」和「加法」哪个更贵。

- 早期 → 可以做结构性调整
- 晚期/收尾 → **只做加法，不删不改**；结构性问题记进 TODO，下个周期做

### 3. 爆炸半径：哪些是公共地盘？

被多服务/多团队依赖的模块，动它的代价不是代码量，是**协调成本**。默认不动。

**自查方式**：`grep -rl "<包路径>" --include="*.go" . | wc -l`，超过 2 个服务就当公共模块处理。

典型公共地盘：`common/`、被多个服务共用的基础服务、被多服务共用的配置加载模块（所有服务启动时都会加载，加一项配置配错就是全站起不来）。

### 4. 帽子：这次是重构还是加功能？

Kent Beck 的 two hats——**两顶帽子不要同时戴**。

- 重构帽：不改对外行为，测试全绿，可独立发布
- 加功能帽：改对外契约，需要客户端配合

一个方案里同时干两件事，后果是：评审时说不清风险边界，出问题时分不清是哪半边坏的。**拆成两个可独立发布的步骤。**

## 什么时候必须问

| 情形 | 动作 |
|---|---|
| 用户已明确说了（「这个没上线」「别动 xxx 公共服务」） | 直接用，别再问 |
| 自查拿到确定事实，且意图只有一种合理解释 | 用，但在方案里**写出这个假设**，给用户一个否决的机会 |
| 自查结果模糊，或事实清楚但意图有多种解释 | **问**。一次问完，别挤牙膏 |
| 完全查不到 | **问** |

**在出方案之前问。** 方案一旦摆出来，讨论就被方案框住了——用户会顺着你的方案挑毛病，而不是回头质疑前提。这次的四轮返工全是这个顺序：先出方案 → 用户补一个约束 → 推倒 → 再出方案。

一次问清楚的成本是一条消息；问晚了的成本是一整轮方案作废。

## 方案呈现规范

1. **每个方案显式标注它假设的约束**——「在『未上线、可以大改』的前提下…」
2. **至少两个方案，且必须包含一个「最小加法」选项**——即使你不推荐它。这个选项的存在，会逼出用户对约束的真实态度
3. **推荐哪个要说清是在哪个约束下最优**，而不是「我觉得这个好」
4. **含删除的方案单独标红**——删除是 one-way door，必须显式确认

## 红旗

出现这些念头就是在跳步：

| 念头 | 现实 |
|---|---|
| 「代码我看懂了，可以出方案了」 | 代码里没有项目阶段，也没有「这是谁的地盘」 |
| 「我查到了 X，所以约束应该是 Y」 | 从事实推断意图。查到的是事实，Y 是猜的——去问 |
| 「先给方案，假设写在后面」 | 方案一出，讨论就被它框住了。先问 |
| 「问这个显得我没查过」 | 带着已查到的事实去问，恰恰显得查过：「查到 X，那这次是按 A 还是 B？」 |
| 「保险起见做兼容」 | 先确认有没有存量依赖。为不存在的依赖打补丁 = 白付维护成本 |
| 「顺手把这块也重构了」 | 两顶帽子。拆开 |
| 「删掉旧的更干净」 | 删除是不可逆的。先问 |
| 「用户没反对，应该可以」 | 沉默不是同意，是还没看到 |
| 「上次他说要可维护性，这次也一样」 | 约束会随阶段变。每次重新确认，不要跨轮次沿用 |

## 与既有 skill 的关系

- `superpowers:brainstorming` 是**通用**的需求澄清流程（HARD-GATE、一次一问、2-3 方案、写设计文档）。**本 skill 不替代它，是它第 3 步「理解 constraints」的具体清单。**
- 涉及接口字段命名/类型时，继续用 `aligning-new-interface-fields`
- 方案落地后的减法审查用 `overengineering-audit`
